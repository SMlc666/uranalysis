# Ura Binary Analysis Platform Design

Date: 2026-06-17

## Purpose

Ura is a long-term binary analysis platform intended to grow toward an IDA/Ghidra-class workflow, while starting with a narrow, verifiable MVP. The first version focuses on practical reverse engineering of ELF64 AArch64 binaries through a reusable engine, project database, CLI, and optional daemon wrapper.

The first version is not a decompiler, debugger, GUI, or multi-architecture platform. Its goal is to prove the core analysis model and project-editing loop.

## Core Decisions

- The engine must be reusable and independent from server/client layers.
- The engine owns project truth and writes project files.
- The initial target is ELF64 AArch64.
- The MVP must support practical reverse-engineering edits, not only static browsing.
- The first client is CLI, with both batch commands and an interactive shell.
- The daemon is optional and thin; it validates future client/server decoupling without becoming the product core.

## System Boundaries

The first version uses a core-first monorepo with four layers.

### `ura-core`

`ura-core` is the authoritative analysis engine. It owns ELF loading, memory mapping, disassembly, function discovery, xrefs, basic CFG construction, project persistence, user edits, and reanalysis.

`ura-core` must not depend on daemon, server, client, HTTP, users, permissions, or task queues.

### `ura-cli`

`ura-cli` is the first user-facing entrypoint. It links directly against `ura-core` and provides both batch commands and an interactive analysis shell.

### `ura-daemon`

`ura-daemon` wraps `ura-core` behind RPC. It provides process isolation and proves that clients can connect without linking the engine directly.

The daemon does not own project truth, does not manage users, does not manage permissions, and does not directly mutate project database internals.

### Future Server And Clients

A future server can manage users, project lists, permissions, task scheduling, collaboration, and Web APIs. Future clients can be Web, desktop, VS Code, or CLI.

All server/client layers must access projects through `ura-core` APIs or the daemon API. They must not write `*.ura` internals directly.

## Project Database

`*.ura` is the engine-owned project file. It is the persistent source of truth for one analyzed binary project.

The first implementation should use SQLite for the project database, with an optional binary blob store for the original input file or large cached data. SQLite is preferred for inspectability, migrations, transaction safety, and simple querying.

### Stored Data

The project stores:

- Project metadata: schema version, engine version, creation time, source file hash, target format, target architecture, and detected loading profile.
- Binary image data: source binary reference or embedded copy, ELF headers, program headers, sections, segments, address mappings, executable regions, and data regions.
- Analysis graph: instructions, basic blocks, functions, call edges, code xrefs, data xrefs, string xrefs, strings, symbols, relocations, imports, and exports.
- User truth: renames, comments, manually created functions, function boundary corrections, manual code/data markings, and tags.
- Analysis cache: function discovery results, xref cache, CFG cache, analysis logs, and diagnostics.

### Authority Rules

Computed truth is generated by the engine and may be replaced by reanalysis.

User truth is created by user edits and must not be silently overwritten by reanalysis.

Reanalysis must use user truth as a constraint. For example, a manually created function should guide subsequent xref and CFG updates.

Analysis cache is rebuildable and must never be more authoritative than user truth.

## ELF64 AArch64 Loader

The first loader supports ELF64 AArch64 inputs. The loader should cover shared objects, executables, relocatable objects, and reasonably identifiable kernel-style ELF files.

The MVP commitment is that supported ELF64 AArch64 files can be opened, mapped, browsed, edited, saved, and reanalyzed. Advanced recovery quality can vary by profile.

### Loader Responsibilities

- Validate ELF class, architecture, endianness, basic file integrity, and key table bounds.
- Build virtual-address to file-offset mappings using program headers as the primary source.
- Use section headers to supplement symbols, strings, relocations, and display data.
- Extract sections, segments, symbols, dynamic table entries, relocations, imports, exports, entry point, init array, and fini array where present.
- Detect loading profile: shared object, executable, relocatable object, kernel-style, or stripped-like.

## Initial Analysis Passes

The first version includes these analysis passes.

### Linear Disassembly Pass

Disassemble executable regions as ARM64 instructions. Store address, size, bytes, mnemonic, operands, fallthrough, branch target, and decode status.

### Function Seed Pass

Create function candidates from entry point, symbols, exports, relocations, branch/call targets, init array, and fini array.

### Recursive Function Pass

From function seeds, recursively construct basic blocks, CFG edges, and function ranges. Indirect branches and unresolved targets should be recorded conservatively instead of guessed aggressively.

### Xref Pass

Create code xrefs, data xrefs, string xrefs, and call edges.

### String Pass

Extract ASCII, UTF-8, and UTF-16 strings. Connect strings to references where address mapping and instruction operands allow it.

### Diagnostic Pass

Record unresolved relocations, invalid instructions, overlapping functions, unmapped addresses, suspicious jump tables, and other analysis issues visible through CLI.

## Explicit Non-Goals For MVP

The first version does not include:

- Decompiler.
- Debugger.
- GUI or Web client.
- Multi-user collaboration.
- PE or Mach-O support.
- Non-ARM64 architectures.
- Full type recovery.
- Advanced jump-table recovery.
- Obfuscation deobfuscation.

## CLI Design

The CLI supports batch commands and an interactive shell. Both must use the same `ura-core` command/query APIs so behavior stays consistent.

### Batch Commands

- `ura new <input.elf> -o <project.ura>`: create a project, import the ELF, and run default analysis.
- `ura analyze <project.ura>`: reanalyze an existing project while preserving user truth.
- `ura info <project.ura>`: show file format, architecture, segments, sections, symbols, function count, xref count, and diagnostic summary.
- `ura funcs <project.ura>`: list functions, with sorting by address, name, size, or xref count.
- `ura disasm <project.ura> <addr>`: disassemble near an address or inside a function.
- `ura xrefs <project.ura> <addr>`: list code, data, call, and string references.
- `ura strings <project.ura>`: list extracted strings with filtering support.
- `ura rename <project.ura> <addr> <name>`: rename a function or symbol.
- `ura comment <project.ura> <addr> <text>`: add or update a comment.
- `ura make-func <project.ura> <addr>`: manually create a function seed and trigger local reanalysis.
- `ura set-func-range <project.ura> <func-addr> <start> <end>`: manually adjust a function range and trigger local reanalysis.

Mutating batch commands save through transactions by default.

### Interactive Shell

`ura shell <project.ura>` opens an interactive shell with commands corresponding to the batch operations:

- `info`
- `funcs`
- `disasm`
- `xrefs`
- `strings`
- `rename`
- `comment`
- `make-func`
- `set-func-range`
- `reanalyze`
- `diagnostics`
- `save`
- `revert`
- `quit`

The shell supports basic address expressions: hexadecimal addresses, `entry`, `func:<name>`, and relative offsets such as `+0x20` from the current cursor/context.

CLI output should support JSON where practical, so scripts and future server/client layers can reuse the same data model.

## Daemon/API Design

`ura-daemon` is a thin RPC wrapper around `ura-core`. It validates the decoupled architecture but does not replace CLI as the primary MVP client.

The first API surface includes:

- `open_project(path)`: open a project and return a session id.
- `close_project(session_id)`: close a project session.
- `get_info(session_id)`: return project summary.
- `list_functions(session_id, filter, sort, page)`: return paged functions.
- `get_disassembly(session_id, address_or_function, range)`: return disassembly.
- `list_xrefs(session_id, address)`: return xrefs.
- `rename_symbol(session_id, address, name)`: rename a function or symbol.
- `set_comment(session_id, address, text)`: set a comment.
- `make_function(session_id, address)`: create a function and trigger local analysis.
- `set_function_range(session_id, function_address, start, end)`: update a user-defined function range and trigger local analysis.
- `reanalyze(session_id, scope)`: perform full or local reanalysis.

The daemon must not directly mutate project storage outside `ura-core`.

## MVP Acceptance Criteria

The MVP is acceptable when:

1. `ura new` can create a `*.ura` project from an ELF64 AArch64 input.
2. The project can be closed and reopened without losing computed results or user truth.
3. The engine extracts ELF metadata, segments, sections, symbols, strings, functions, basic blocks, and xrefs.
4. The user can rename, comment, create functions, and make basic function boundary corrections.
5. User edits persist in the project and are not silently overwritten by reanalysis.
6. Reanalysis updates xrefs/CFG where possible while respecting user truth.
7. Batch CLI commands and `ura shell` expose the same core operations.
8. `ura-daemon` can open a project, list functions, fetch disassembly, and write a comment through RPC.
9. Tests cover at least one Android `.so`, one Linux AArch64 executable, and one relocatable `.o`.
10. Kernel-style ELF support is tested only for opening and basic metadata/section extraction in the MVP.

## Testing Strategy

Tests should be built around small, reproducible sample binaries.

Unit tests cover ELF validation, address mapping, project DB migrations, analysis graph persistence, and command API behavior.

Integration tests run `ura new`, `ura info`, `ura funcs`, `ura disasm`, `ura xrefs`, `ura rename`, `ura comment`, `ura make-func`, and `ura analyze` against sample projects.

Daemon tests use a minimal external client to prove that projects can be opened, queried, and edited without linking directly to `ura-core`.

Regression tests should preserve project database compatibility across schema migrations once the first schema is published.

## Open Risks

- Function discovery quality on stripped ARM64 binaries may be weak in the first version.
- Indirect branches and jump tables should be recorded conservatively until a dedicated recovery pass exists.
- Kernel-style ELF support can easily expand scope; MVP support must stay limited to opening and metadata extraction.
- SQLite is suitable for the first version, but instruction/xref-heavy projects may later need specialized caching.
- The daemon API should remain thin until `ura-core` APIs stabilize.
